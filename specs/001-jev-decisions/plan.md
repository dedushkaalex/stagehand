# План реализации и проверки

## Архитектура

`packages/sdk-ts/src/decisionAct.ts` получает AX snapshot, локально уплотняет кандидатов, вызывает `DecisionProvider`, повторно валидирует цель, исполняет одно действие и обязательный `verify`. `decisionProvider.ts` задаёт контракт и Jev transport. Исходный `act()` сохраняется для baseline.

`packages/sdk-ts/examples/decision-benchmark.ts` содержит fixture/Google Flights harness. В неопубликованном облачном прототипе OpenCode подготовка вынесена в отдельный модуль; предполагаемый baseline переводит оригинальные инструкции и schema Stagehand в Chat Completions, а Jev использует System One. Для будущей реализации запрещена подмена провайдера, тарифа или модели при ошибке. Этот OpenCode модуль отсутствует в опубликованной ветке.

## Этапы

1. Зафиксировать исходный upstream SHA, неизменность baseline/runtime и хеши загружаемого расширения. Проверка исходников не равна аттестации собранного расширения.
2. Поддерживать unit/contract тесты выбора, отказов, stale DOM, deadlines, provider schema, нулевых сетевых вызовов в blocked и арифметики бюджета.
3. На рабочем браузерном окружении вручную выполнить mock smoke: это проверка интеграции, не качества Jev. Добавить отдельные layout fixtures для перекрытия, offscreen, responsive и динамического DOM.
4. До живого OpenCode запуска реализовать авторитетную проверку subscription-only/отсутствия Extra Usage fallback, верхние границы начислений и постоянный ledger на всю задачу с резервированием незавершённых запросов. Не снимать gate простым env-флагом.
5. После выполнения этих условий и разрешения расходов пользователь вручную запускает одинаковые fixture и Google Flights сценарии для DeepSeek V4.1 Flash baseline и Jev enhanced. Локальный автоматический запуск остановлен; эта документация его не возобновляет.
6. Сохранить обезличенный отчёт: версии/commit/model ID, сценарий, порядок arms, успешность, шаги, wall time, phase time, запросы, input/output/cached tokens, cost USD или null, причины отказов и ссылки на локальные evidence.

## Методика сравнения

Один checkout и runtime; новый профиль для каждого arm; одинаковые postconditions; чередование порядка arms; без скрытого warm-up и retries. Публиковать время по всем попыткам и отдельно по успешным вместе с success rate. Ранний отказ не считать ускорением. В Google Flights текущий один кандидат измеряет ограниченный диагностический шаг, не сложность общего выбора.

## Риски и решения

- Потеря правильного кандидата при compaction: счётчики и репрезентативные fixtures; отдельное измерение recall.
- Состояние меняется после snapshot: revalidation и отказ.
- Тайм-аут после отправленного действия/запроса: неопределённый результат и ограниченная cleanup; не обещать отсутствие списания.
- Подписка может перейти на balance: fail-closed до авторитетного подтверждения; проверка billing_source после ответа недостаточна для предотвращения расхода.
- Артефакты могут содержать данные сайта: только локальное хранение, проверка перед публикацией.

## Ограничения окружения

Работа выполняется в облаке, только в fork/feature branch. Main/upstream PR не меняются. Browser smoke в доступной среде ранее остановился на SIGABRT Chromium до debugging port; полный `pnpm check` ранее блокировался средой. Это фиксируется как ограничение, а не зелёный E2E.
