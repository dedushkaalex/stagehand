# Спецификация: ограниченные решения Jev в Stagehand

Дата: 2026-11-03. Статус: direct Jev реализован в ветке; OpenCode — целевой план и неопубликованная облачная подготовка; живое сравнение не выполнено.
Ветка: `feat/jev-decisions`, только публичный fork `dedushkaalex/stagehand`.

## Цель

Снизить объём контекста и стоимость выбора UI-элемента, сохранив проверяемый результат. Новый `decisionAct()` дополняет исходный `act()`, а не подменяет его. Любые заявления об ускорении, экономии или качестве требуют настоящих измерений.

## Пользовательские сценарии и приёмка

1. Приложение задаёт инструкцию, допустимый метод (`click`, `fill`, `selectOption`), значения и обязательный `verify`. Локальный код строит компактный список из DOM/AX. Обычная LLM не используется для предварительного отбора. Провайдер выбирает только известный ID или `none`; XPath остаётся локально.
2. Перед действием повторно проверяются актуальность snapshot, идентичность, уникальность и видимость цели. Низкая уверенность, неизвестный ID, тайм-аут, изменившаяся страница и `none` приводят к отказу без fallback или автоматического повтора.
3. Успех означает исполнение и семантическую postcondition. Для fixture проверяются значения направления/дат/класса, точный результат и единственная отправка. Для Google Flights текущий сценарий ограничен открытием departure picker и видимым диалогом; это не полный поиск и не бронирование.
4. Jev direct реализует, а будущий Jev через OpenCode должен реализовать один контракт `DecisionProvider`. Baseline через OpenCode должен использовать `deepseek-v4.1-flash`; Jev через OpenCode — `jev-1.13`. Подготовка адаптера не доказывает доступность сервиса.
5. Честное сравнение использует одинаковые сценарии, шаги, проверки, checkout и браузерный runtime. Фиксируются время, доля успеха, завершённые шаги, запросы, токены, стоимость и причины отказов. Неизвестные значения равны `null`, а не нулю.

## Требования

- FR-01: детерминированная фильтрация/ранжирование AX-кандидатов и ограниченный размер списка (по умолчанию 24); счётчики кандидатов доступны для анализа потерь recall.
- FR-02: внешний провайдер получает только минимальные описания, инструкцию и явный state. Он не определяет произвольный код, локатор или вводимые значения.
- FR-03: общий deadline включает действие и проверку; после неопределённого результата сначала выясняется состояние, действие не повторяется автоматически.
- FR-04: поведенческие assertions обязательны. Видимость/уникальность/диалог проверяются сейчас; более широкие layout assertions (геометрия, перекрытие, viewport, responsive) — отдельная незавершённая работа, не уже пройденный тест.
- FR-05: при ошибке сохраняются screenshot и snapshot либо явная ошибка их сохранения. Артефакты локальны, исключены из Git и не публикуются автоматически.
- FR-06: совокупный предел задачи $1, без сброса при перезапуске. Пока нет подтверждённых верхних границ цены, durable ledger и subscription-only preflight, реальные OpenCode запросы запрещены.
- FR-07: отсутствие ключей/разрешения даёт blocked до браузера и providerCalls=0. Будущий OpenCode должен оставаться blocked даже с ключом и самодельным флагом подтверждения; текущая публичная ветка ещё не содержит этого режима.
- FR-08: никаких бронирований, платежей, входа в аккаунт, CAPTCHA или передачи личных данных. Только синтетические fixtures и публичный ограниченный Google Flights сценарий.

## Что не входит в доказанный результат

Полный Google Flights поиск, обход защит сайта, автономный агент, калибровка confidence, преимущество одной модели, гарантированная экономия, живая совместимость structured output, жёсткая гарантия биллинга. Для этого нужны отдельные проверки и, где требуется, разрешения.

## Критерий завершения

Реализация считается проверенной end-to-end только после разрешённого запуска обеих ветвей на одинаковых задачах, успешных semantic/layout checks и отчёта с доказательствами. До этого unit/contract результаты отмечаются отдельно от browser/model benchmark.
